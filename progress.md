**Status legend:** `[ ]` not started · `[~]` in progress · `[x]` done · `[?]` blocked / needs decision

---

## Repo map (quick reference)

- `backend/`  — Java 17, Vert.x reactive verticles, MSSQL. Dispatch by `processingCode` over the event bus (`main/EntryPoint.java`). Services in `services/`.
- `frontend/` — Vue 3 + Vuetify 4 + Vite + TS. Single `dispatch()` client (`src/api/client.ts`), codes catalog (`src/api/processingCodes.ts`), pages in `src/pages/`.
- `mobile/agent/` — consolidated Android field app, Morpho 6.42/6.15 product flavors, offline WorkManager sync, voucher redemption, and face-enrollment foundation. `mobile/nca/` is legacy reference code.
- `database/` — MSSQL migrations (`migrations/`) + seed. Idempotent, no FK constraints by convention.

## Roadmap / work to be done

### Mobile — field agent app
Context: the legacy plan below targeted `mobile/nca`; active implementation now lives in the consolidated `mobile/agent` app (`com.biopay.agent`) with Morpho product flavors and offline WorkManager sync. Voucher redemption and the secure face-enrollment/sync foundation are implemented there. Production face capture/matching remains blocked as recorded in the current audit.

#### A. Facial recognition (register by face / fingerprint / both)
- **SDK choice (recommended): fully on-device, offline-first** — Google **ML Kit Face Detection** (free) to find/validate a single clear face + **TensorFlow Lite MobileFaceNet** (or FaceNet) to compute a 128/512-d embedding for 1:1 verification. Add liveness later (commercial SDKs — Innovatrics/Regula/Neurotechnology — if higher assurance is required; they carry licensing cost). Rationale: matches the existing offline-first, no-signal-at-capture model and needs no per-match server call.
- **Enrollment**: the "Register by: Fingerprint / Face / Both" choice, local face record, encrypted backend storage, and sync contract are implemented. Remaining: integrate the approved engine/camera flow and protect the offline SQLite biometric store with a device-compatible keystore/database-encryption design after target Android versions are confirmed.
- **Backend**: implemented migration `012_face_embeddings.sql`, encrypted/idempotent `ENROLL_FACE`, `SYNC_FACES`, and face records in `BIOMETRIC_LOGIN`. Identity matching intentionally stays on-device; no insecure server placeholder is exposed.
- **Verification at payment**: `PaymentVerificationActivity` offers fingerprint OR face; face path captures → embeds → compares against the synced enrolled embedding for the household on-device (offline).
- **Data model**: add a `registration_method` (FINGERPRINT/FACE/BOTH) column to households/alternates so the app knows which verification to offer.

#### B. Voucher redemption on device
- **Backend is already primed**: `REDEEM_VOUCHER` accepts optional biometric-match fields (matchedFingerprint/latitude/longitude) for exactly this flow (see `Voucher.java` javadoc); the `vouchers` table has `redeemed_by_officer_id`, `matched_fp`, lat/long. Add `SYNC_VOUCHERS` (mirror `SYNC_PAYMENTS`) so issued vouchers can be validated offline.
- **Mobile flow**: new `VoucherRedemptionActivity` — scan the printed voucher QR (add `zxing-android-embedded`) or pick from the synced list → verify household biometric (fingerprint/face) → call `REDEEM_VOUCHER { voucherCode, matchedFingerprint, latitude, longitude }`. Queue offline and sync via the existing `SyncAdapter`. Add a "Redeem Voucher" entry to `MainActivity` gated by the VOUCHERS org module; add a `RecyclerVoucherAdapter`.
- **QR note**: the web-printed voucher QR currently encodes the **household number**; for direct scan-to-redeem, either encode `voucher_code` on the voucher QR or have the app resolve the household → its issued vouchers.

- **Bug 1 (fixed): Settings crashed on open.** `btnTestScanner` (and separately `btnSendFeedback`) in the new `activity_settings.xml` used `style="@style/Widget.Material3.Button.TextButton"` with an explicit `layout_width` but no `layout_height` — that system style doesn't supply one (unlike the project's own `BioPay.*` button styles, which do), so `LayoutInflater` threw `UnsupportedOperationException: You must supply a layout_height attribute` and took down the whole screen. Added the missing `layout_height="wrap_content"` to both.
- **Bug 2 (fixed): Settings crashed again on resume, this time from the new Biometrics status check.** `refreshScannerStatus()` calls `BiometricDeviceFactory.create().isAvailable(this)`, which was never called anywhere else in the app before this redesign. On this test phone (no real Morpho scanner ever attached) that touches `USBManager`'s static initializer, which throws `UnsatisfiedLinkError: libNativeMorphoSmartSDK_6.42.0.0.so not found` — an `Error`, not an `Exception`. Both `MorphoDeviceAdapter.isAvailable()` implementations (6.42 and 6.15 flavors) already had a `catch (Exception ex) { return false; }` guard, which does not catch `Error`/`Throwable`, so it propagated and crashed. Widened both to `catch (Throwable ex)` — the interface's own contract says "best-effort check... can still fail," so it must degrade to `false`, never throw. This was a latent bug in existing code, just never exercised until something finally called `isAvailable()` proactively.
- **Confirmed working after both fixes:** app renamed to "BioPay" (splash, launcher icon/label); Settings renders all sections (Account, Notifications, Connection & sync, Biometrics, Security, Data & storage, About, Log out) with real data (1 household, 0 pending, version `1.1-morpho642`); Biometrics correctly shows "Not connected" instead of crashing when no scanner is attached; Account row navigates to Profile; App lock toggle persists and — on a cold relaunch — correctly summons the OS `BiometricPromptRoot` window gating `SplashActivity` (confirmed via `dumpsys window` focus, since the secure prompt surface itself isn't screenshot-capturable), and cancelling it correctly fails closed (app stays locked with a "Try again" button) rather than leaking through to Home; Log out shows the confirmation dialog and correctly returns to the Login screen with the session cleared. Logged back in afterward to leave the device in a normal signed-in state.
